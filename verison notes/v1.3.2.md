# Micforge v1.3.2 Release Notes: Speech Onset Preservation & Discord 2x-Speed Elimination

Micforge version 1.3.2 addresses two subtle real-time audio pipeline glitches:
1. **First-Word Cutting (Onset Consonant Clipping):** When beginning to speak after silence, leading unvoiced consonants (/p/, /t/, /k/, /s/, /h/, /ch/) were intermittently attenuated or silenced.
2. **Discord 2x-Speed Audio ("Chipmunk" Catch-Up Mode):** Audio fed to Discord or virtual audio cables would occasionally play back at 1.5x–2.0x accelerated speed following DSP stalls or brief pauses.

---

## 1. Root Cause Pinpoint & Engineering Analysis

### Issue A: First-Word Cutting (Onset Clipping)
- **The Acoustic Trap:** Spoken words almost always begin with unvoiced consonants (plosives, fricatives, affricates) rather than voiced vowels. These consonants lack strong harmonic periodicity in the 300–4000 Hz vocal cord range; their energy is concentrated in high-frequency turbulence (4–10 kHz) or transient pressure pulses.
- **The VAD Ramp Delay:** In v1.3.1, the neural mask speech probability (`raw_vad`) for initial consonants started at ~0.20–0.30. Because temporal smoothing used an attack coefficient of 0.75, it required 2–4 STFT frames (32–64 ms) to ramp across the hard `speech_prob >= 0.45` threshold.
- **Zero Lookahead:** The noise gate was positioned after `SpectralRack` with zero lookahead buffer. While the VAD spent 32–64 ms recognizing speech, the gate was clamped shut at `-20 dB` or `-40 dB`, permanently muting the first consonant of the user's sentence.

### Issue B: Discord 2x-Speed Audio (NetEQ Accelerate Mode)
- **WebRTC NetEQ Mechanism:** Discord captures microphone audio through WASAPI and routes it into Google's WebRTC VoiceEngine. WebRTC maintains an adaptive jitter buffer (`NetEQ`). If incoming packets experience a dropout followed by a delayed backlog, NetEQ measures an excessive packet delay ($> 60\text{ ms}$). To restore real-time interactive conversation, WebRTC activates **`kModeAccelerate`**, using pitch-synchronous overlap-add (WSOLA) time-stretching to play speech back at **1.5x to 2.0x speed** until the backlog is cleared.
- **The Buffer Backlog Bug in Micforge:** When an ONNX inference spike or Windows thread scheduling hiccup occurred, the input callback took $> 10\text{ ms}$. `OutputSink._callback` experienced a momentary underrun. In v1.3.1, the ring buffer had 48,000 samples (1 full second) of capacity with no upper latency clamp. When the delayed input blocks arrived, they piled up in the ring buffer. Because clock drift correction only corrected 1 sample every 1.5 seconds, that extra 40–100 ms of latency lingered in the buffer for minutes. Whenever Discord polled the stream, WebRTC received a burst of packets, permanently triggering 2x-speed playback.
- **Sample Rate Mismatch:** In `SpectralRack`, `_resample_ratio == 3` only handled 48 kHz. If a user connected a 32 kHz Bluetooth headset (Hands-Free Profile) or a 44.1 kHz USB microphone, `SpectralRack` did not resample, treating 32 kHz samples as 16 kHz—producing an exact **2.0x frequency shift and speedup**!
- **Audio Thread Contention:** Every 50 ms (5 blocks), `_on_input` executed `np.percentile` on 12 different stages inside the PortAudio input callback thread, performing memory allocations and array sorting directly in the real-time audio path.

## 2. Architecture & DSP Fixes Implemented

### 1. Zero-Allocation Circular Lookahead Buffer in `NoiseGate`
A 10 ms pre-allocated circular lookahead buffer (`int(0.010 * sample_rate)` = 480 samples @ 48 kHz) was integrated into `NoiseGate`. The detector analyzes the incoming block in real-time, while the audio signal passing through the gain stage is delayed by 10 ms. When speech onset is detected, the gate is already open for the leading consonant, preserving 100% of the acoustic attack transient.

### 2. Dual-Trigger Speech Onset Detector
Replaced the rigid `speech_prob >= 0.45` check with an energy-coupled dual trigger:
- **Speech Onset Trigger:** Opens if `speech_prob >= 0.28` OR (`speech_prob >= 0.16` AND block RMS $> \text{threshold\_db}$).
- **Hold Hysteresis:** Retains gate open if `speech_prob >= 0.14` OR (block RMS $> \text{close\_thr}$ AND `speech_prob >= 0.10`).
- **Hold Duration:** Increased default `hold_ms` to 120 ms to bridge natural stop-consonant closures between words without gate chattering.

### 3. Anti-Burst Latency Ceiling in `OutputSink.push()`
In `OutputSink.push()`, ring buffer fill is strictly clamped to an anti-burst latency ceiling:
$$\text{max\_cushion} = \text{prefill} + 1.0 \times \text{block} \quad (\approx 25\text{ ms})$$
If a thread scheduling stall causes multiple blocks to arrive in quick succession, any excess beyond 25 ms is immediately dropped. The ring buffer never accumulates a backlog, and Discord's WebRTC NetEQ jitter buffer **never triggers 2x-speed Accelerate mode**.

### 4. Universal Polyphase FIR & Rational Resampling in `SpectralRack`
`SpectralRack` now supports all hardware and virtual sample rates:
- **48,000 Hz $\leftrightarrow$ 16,000 Hz:** Optimized 3:1 polyphase 31-tap FIR decimation/interpolation ($0\text{ dB}$ passband ripple, $> 65\text{ dB}$ stopband rejection).
- **32,000 Hz $\leftrightarrow$ 16,000 Hz:** Fast 2:1 polyphase 31-tap FIR decimation/interpolation.
- **16,000 Hz $\leftrightarrow$ 16,000 Hz:** Direct 1:1 pass-through.
- **44,100 Hz / 96,000 Hz $\leftrightarrow$ 16,000 Hz:** Stateful rational polyphase resampling (`scipy.signal.resample_poly`), completely preventing pitch and speed warping on non-48k devices.

### 5. Audio Thread Jitter Elimination
`stage_timings()` and its 12 `np.percentile` array sorts were moved entirely out of the PortAudio input callback `_on_input` and into `AudioEngine.snapshot()`. The real-time audio thread now executes strictly in nanoseconds with zero sorting and zero allocations.
